# Project documentation

A tool project can publish the documentation that lives in its own repository: guides written in Markdown and, later, a reference generated by a command. This page is the entry point: it describes how guides become pages; a later feature adds the reference. Nothing is repeated from the page that already exists:

- **Where the documentation comes from**, the `docs` block of `project.yaml` (`source`, `github`, `guides`, `reference`), the fetching of git repositories and folders, the cache, git safety, the failures and the manifest entry are described in [Where a project's documentation comes from](docs-sources.md). That page is the canonical description of the `docs` block.
- The page of the project that links to its documentation is described in [Projects](projects.md).

## Guides: how they become pages

The guides named in the `docs` block of `project.yaml` are rendered with the same Markdown pipeline and the same theme as the rest of the site, at `/{projects}/{slug}/{docs}/{page}/` (`/made/kerfcalc/docs/usage/` with the defaults; `urls.projects` and `urls.docs` move them). The files come from the fetched source ([Where a project's documentation comes from](docs-sources.md)); nothing is rendered unless the project has at least one guide.

### Which files, in which order

- A guide publishes the Markdown files (`.md` and `.markdown`) of its `dir` that its `include` patterns select and its `exclude` patterns leave out (syntax in [docs-sources.md](docs-sources.md#guides)). `.git` and `node_modules` folders are never searched, and a symbolic link to a folder is not followed.
- **No file selected is an error**, naming the guide: there is no fallback to empty documentation.
- **Sidebar order:** the docs index first; then, for each guide in the order they are listed, the files named in `order` (in that order), then the remaining files by path (code-point order, so `Z.md` is before `a.md`). A name in `order` that is not a published file is a warning. A file selected by two guides belongs to the first.
- **Bounds:** at most 500 pages for a project and 1 MiB for a file; a file that is not valid UTF-8 is an error; a byte order mark is dropped and Windows line endings are accepted, with line numbers in findings unchanged.

### Addresses

The address of a page is its path in the guide, without `.md`, in lower case, with every run of characters other than letters (a-z) and digits as one dash, and folders as path segments: `Api/Error_Codes.md` is `.../docs/api/error-codes/`. A `README` or `index` file in a sub folder stands for the folder (`api/README.md` is `.../docs/api/`). A name from which no address can be made (only non-Latin letters) is an error that asks for a rename.

The **docs index** (`/{projects}/{slug}/{docs}/`, the target of the documentation link) is the `index.md`, else `README.md`, in the folder of the **first** guide; the other of the two is then an ordinary page (`.../docs/readme/`). If the folder has neither, the build writes a plain index that lists the pages, so the link always leads somewhere.

Two files with the same address (`a_b.md` and `a-b.md`), an address that begins with `reference` or `search` (reserved for the generated reference and for search), and a page written to a file another page also uses are errors that name the files.

### Titles and metadata

The title of a page is its **first heading of level 1**, which is then left out of the body (the template writes it once, with its `id`, so links to it keep working). A page without one is titled from its file name, `how_to-install.md` being "How To Install"; the docs index is "Documentation". The `<title>`, description (the first words of the text), canonical address and Open Graph tags are made like those of other pages (the preview picture is the project's card). A page with four or more headings of level 2 or 3 gets the table of contents posts have, from the same partial. Docs pages are in the sitemap and in the manifest: as `pages` of type `docs`, and as `docs.pages` of the project (`url`, `file`, `source` (the path in the documentation source, null for a generated index) and `title`).

### Link rewriting

A link is resolved from the folder of the page that holds it; a link that starts with `/` is resolved from the root of the repository, as it is on GitHub. `?query` and `#anchor` are kept. Every finding is located as `{repo}:{path}:{line}:{column}`, where `{repo}` is the name of the folder for a folder source and the name of the GitHub repository (else the project's slug) for a git source: `sample-tool:docs/usage.md:7:1 broken link 'gone.md' (...)`.

| The link leads to | Result |
| --- | --- |
| another published guide file (`usage.md`, `./usage.md#options`), or the folder of the docs index (`./`) | the site address of the page, anchor kept; the anchor has to be a heading or an id of that page |
| `#anchor` | left as it is; it has to be a heading or an id of the page itself (`#top` always works) |
| a file of the repository that is not published (a source file, `LICENSE`, `../CHANGELOG.md`, `../README.md`) | `https://github.com/{owner}/{repo}/blob/{ref}/{path}` |
| a folder of the repository | `https://github.com/{owner}/{repo}/tree/{ref}/{path}` (the root is `.../tree/{ref}`) |
| `https:`, `http:`, `mailto:`, `//host/...` | left alone |
| any other scheme (`javascript:`, `data:`, `vbscript:`, `file:`) | **error**; the page carries `#` instead |
| a file that does not exist, or one that exists with other capitalisation | **error** |
| a path that goes above the root of the repository, or through a symbolic link that leads out of it | **error** |
| an unpublished file or folder, when the `docs` block has no `github` setting | **error**, asking for the setting |

Path segments of GitHub addresses are percent-encoded. The `{ref}` is the configured `ref` for a git source (a branch or tag). For a folder source it is the full commit when the folder is itself the root of a git repository (it has a `.git`) and the commit is known, because a commit never moves; otherwise `main`, because the commit of a larger repository that merely contains the folder is not a commit of the GitHub repository.

Links written as raw HTML are not rewritten (they are left as written and the output check reports the ones that lead nowhere), but every address in raw HTML is checked for a refused scheme.

### Images

A relative image is read from the repository (through the same containment as every other file), must exist, and goes through the image pipeline like a post's: responsive WebP variants, width and height, lazy loading, a warning without alt text, the site's metadata policy, the viewer, and an entry in the manifest's `images`. `http:` and `https:` images are left as they are. **SVG images are not published from a guide** (a clear error asks for a PNG, WebP or JPEG), and so are `data:` pictures and anything else that is not JPEG, PNG, WebP or HEIC. A missing image is an error located at the image. Carousels (`:::carousel`) work as in posts; `::map` is left out with a warning; any other directive is an error with its line.

### The template

`docs.njk` extends `base.njk`, so the header, footer, theme switch and styles are the site's. It writes: breadcrumbs (projects, the project, the documentation, the page); a `<nav>` with the label "{project}: documentation pages" listing the pages in order with the current one marked `aria-current="page"`; the page; previous and next links; and, when the `github` repository is known, a link "View this page on GitHub" to the file. On a narrow screen (360 px) the sidebar is above the text; from 60 rem it is beside it and stays in view. No script is needed and nothing is animated. Each part is a block (`docs_breadcrumbs`, `docs_sidebar`, `docs_header`, `toc`, `docs_body`, `docs_pager`, `docs_source`); a theme can replace one (`{% extends "coffer:docs.njk" %}`). The template receives `project`, `projectsUrl`, `toc` and `docs` (`isIndex`, `generated`, `indexUrl`, `url`, `titleId`, `sidebar` (`{ title, url, current }`), `previous`, `next` and `sourceUrl`).

### The link to the documentation

The tool page and the project block of a post link to `/{projects}/{slug}/{docs}/` if and only if the build rendered documentation pages for the project. With `guides` empty the docs section is empty and the link is hidden; a `docs` block with a `reference` only (a later feature) behaves the same until the reference adds pages of its own.

### Trust

See [Trust](docs-sources.md#trust): raw HTML in a guide is passed through like in your own posts; addresses with unsafe schemes are refused.

The `coffer docs fetch` command (see [Build](build.md)) fetches the sources without building anything.
